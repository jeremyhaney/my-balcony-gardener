# Phase 8G.3.2 - Public Live Customer Example

Status: Implemented and locally validated; production deployment and hosted validation are not yet claimed

Date: 2026-08-26

Scope: Temporary public `/demo` presentation boundary until the planned deterministic Phase 8I Demo replaces the live example

## Decision

Keep `/support` authenticated and engineering-oriented. Do not weaken Support access to gather remote design feedback.

Until the deterministic Phase 8I Demo exists, `/demo` is a public live customer-facing example backed by the existing intentionally public read-only Balcony02 views. It is labeled `Live Example` rather than implying deterministic or curated demo data.

The temporary page retains:

- current interpreted garden readings and adaptive scales;
- condition labels, values, trends, and sparklines;
- full-range current-position mini-maps;
- Garden Reading Quality;
- automatic refresh aligned with the 15-minute telemetry cadence;
- history-window controls through 24 hours and chart-series controls;
- live public Balcony02 evidence.

The public/customer presentation excludes:

- the Support diagnostics panel;
- raw ADC values and the RMI calculation;
- sensor keys, families, channels, and physical IDs;
- source-row, batch, device, storage, and provenance fields;
- formula constants, calculation units, and derived-input evidence;
- consecutive paired-evidence failure counters;
- Support capability/configuration evidence;
- the meaningless one-option Demo device selector;
- the public manual Refresh control and last-refreshed line;
- public history queries longer than 24 hours.

Longer history choices remain visible but disabled and are labeled `customer only`. The public query path independently constrains URL and state values to 24 hours, so changing `?window=7d` or manipulating the control cannot request the larger window. Public scheduled refresh runs every 15 minutes while visible, matching the ordinary telemetry cadence; protected Customer and Support retain their five-minute visible cadence and manual Refresh control.

These controls reduce requests generated by the ordinary public UI, but they are not server-side rate limiting. A visitor or automated client can still reload the page or call a public endpoint directly. True rate limiting must be enforced before or at the API/database boundary—such as Cloudflare, an API gateway, an Edge Function, or a database-facing service—and should cap requests per client or time interval, return `429 Too Many Requests` when the cap is exceeded, and optionally cache identical read-only responses. That defense is separate future infrastructure work.

Expanding an ordinary or derived public/customer reading shows only its interpreted state and latest reading time. `/support` retains the full engineering presentation.

## Boundary

This is a presentation boundary, not a data-secrecy claim. `/demo` continues to use the deliberately public hosted measurement and safe diagnostics views, and the current frontend derives RMI from public raw evidence. If raw ADC later becomes sensitive, a narrower public database contract that exposes derived RMI instead would be required; hiding fields in React would not be a security boundary.

No Support/customer authorization, RLS, public view, query selection, Supabase schema, firmware, telemetry, watering behavior, reservoir safety, or command/control boundary changes in this phase.
